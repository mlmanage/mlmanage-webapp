# Jobs-first navigation

MLManage is a dark-only job manager. Browser API requests stay on the same-origin `/api/mlmanage` proxy.

- **Jobs** is the landing view. It normalizes queued records, scheduled records, and unlinked legacy Tasks into one dense list. Selecting a row exposes configuration — owner, project, priority, parallel copies, gang/MPI placement, dependencies, GPU slice — plus linked Task logs (with a selectable number of lines and a save-to-file action), results, downloads, and cancellation. A scheduled job can extend its own reservation window.
- **New job** is a labelled, full-height sheet. Its only timing choices are **As soon as possible** (`POST /queue`) and **Schedule** (`POST /jobs`). Both persist `display_name`. Direct Task creation is intentionally absent. Queue-level scheduling — priority, parallel copies, start-all-together (gang), MPI, waiting on other queued jobs, and the MIG slice for a scheduled window — lives in a collapsed **Advanced scheduling** disclosure so the default path stays short.
- **Capacity** consolidates inventory with each card's sharing mode and MIG capability, reserved windows, the shared schedule held by everyone, and workspace storage. Users reserve, extend and release accelerator windows directly, export or subscribe to the schedule as iCal, and import windows from an `.ics` file. Administrators configure a card's sharing mode (full, time sharing, concurrent sharing, or MIG slice counts) from the inventory row; administrators and power users create group shared storage.
- **Projects** contains group, project, and shared storage context.
- **Usage** contains analytics and read-only monitoring: headline cards for jobs, allocated GPU time, energy, carbon footprint and average utilization, a per-scope table with the efficiency note, a CSV export, and hardware telemetry with units.
- **My account** is read-only and shows what the backend records for the signed-in user: role, notification addresses, group, scheduling priority, allocation (including per-model accelerator and VRAM limits), workspace sizes, project access, and the windows they are holding.
- **Administration** contains users, cleanup information, and the activity log, and is admin-only. Account editing exposes the fields `PUT /users/{username}` actually accepts and shows the create-time allocation read-only. **Activity log** reads `GET /audit-log`: who did what, to which object, and how it ended (succeeded, not permitted, rejected, failed), including every sign-in attempt. It filters by period, person, action, result and free text, pages through the history, and exports the current page as CSV. It loads only while this view is open, because it is the one endpoint every other role is refused — polling it elsewhere would append a denied record to the log it displays.

Container images are selected, referenced externally, or uploaded as docker-save archives inside New job. Uploads carry a name, tag and visibility (only me, a project, a group, or everyone); the compact library view changes who can use an existing image. Images is no longer primary navigation.

On narrow screens the navigation is a modal drawer. Jobs compose as list followed by detail rather than a squeezed desktop split panel. New job remains a full-screen sheet. Readonly users can inspect all permitted views, but never see New job or destructive controls.
